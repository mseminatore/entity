OOP vs. ECS iteration

A movement update (pos += vel * dt) run four ways over the same scene. Lower ns per entity is better; the breakpoint is where the ECS gets ≥ 5% faster than the classic GameObject* loop and stays faster at every larger entity count.

How to read this

OOP GameObject*: a std::vector<GameObject*> of heap objects, mixed movers and static props, updated through a virtual Update(). Every object is visited and its whole cache line(s) pulled in, including cold payload.

ECS for_each: view<Position, Velocity>().for_each(...) from the entity library — only movers, but with the library's mutation-safe per-entity bookkeeping (an entity-list snapshot and a liveness lookup per entity).

ECS for_each_chunk: the library's fast path — a plain loop over each archetype's contiguous Position and Velocity columns.

Raw SoA arrays: two hand-written arrays of movers only; the upper bound for this layout.

Why the ECS can win even when everything fits in L1: with movers and props shuffled together, the target of each virtual Update() call is unpredictable, so the OOP loop also pays branch mispredictions and a call per object, and can't be vectorized. That's a cost of heterogeneous GameObject* iteration, separate from cache behavior. The cache effect shows as the growth in OOP's ns/entity as N crosses each cache boundary, while the chunk and SoA lines stay flat. Compare the 100%-moving series, where the call target is always the same, to see the cache effect with branch costs mostly removed.

The dashed vertical lines mark the entity count at which the OOP working set (objects + pointer array) outgrows each cache level. Heap fragmentation only changes the OOP layout; ECS and SoA storage is contiguous by construction.
